# РОСПАРК — редакционная политика и стиль текстов

Статус: рабочая документация v1.1  
Дата: 2026-05-04

## Назначение

Документ задаёт правила для текстов сайта РОСПАРК. Цель — писать понятно для российского B2B-заказчика: директоров, управляющих компаний, служб безопасности, инженеров, застройщиков, торговых центров и бизнес-центров.

## Главный принцип

Пишем простым инженерным русским языком. Сайт должен звучать как надёжный подрядчик, который понимает объект, оборудование, эксплуатацию и ответственность за результат.

## Тон

Тон сайта:

- деловой;
- уверенный;
- инженерный;
- без рекламного шума;
- без чрезмерных обещаний;
- с акцентом на практическую пользу.

Не нужно писать как стартап-презентация. Нужно писать как компания, которая может приехать на объект, спроектировать систему, смонтировать оборудование и отвечать за работу парковки.

Важно: не запрещаем все иностранные слова механически. Если термин привычен для аудитории и короче русского аналога, его можно оставить. Но если есть понятный русский вариант — выбираем русский.

## Как описывать РОСПАРК

Правильно:

```text
РОСПАРК проектирует, внедряет и сопровождает парковочные системы под ключ.
```

Правильно:

```text
Мы отвечаем не только за поставку оборудования, но и за работоспособность парковки после запуска.
```

Слабее:

```text
Мы предлагаем инновационную платформу для управления парковочным пространством.
```

## Как описывать оборудование

Писать не только название, а роль в системе:

```text
Терминал оплаты принимает оплату от разовых посетителей и передаёт данные в парковочную систему.
```

```text
Въездная стойка выдаёт билет или карту, открывает сессию клиента и управляет шлагбаумом по сценарию объекта.
```

## Как описывать распознавание номеров

Не писать слишком абстрактно. Нужно объяснять практическую пользу:

```text
Камера распознаёт номер автомобиля, система открывает сессию и принимает решение о проезде без участия оператора.
```

Если точность зависит от условий, не обещать абсолютный результат:

```text
Качество распознавания зависит от освещения, угла установки камеры, загрязнения номера и скорости автомобиля. На этапе внедрения мы подбираем настройки под конкретный объект.
```

## Как описывать поддержку

Лучше:

```text
После запуска мы остаёмся на сопровождении: помогаем с настройками, обновлениями, диагностикой и восстановлением работы системы.
```

Хуже:

```text
Мы обеспечиваем premium support и SLA.
```

## Структура хорошего блока

Для коммерческого блока желательно использовать порядок:

1. Проблема клиента.
2. Как это решает РОСПАРК.
3. Что получает объект.
4. Почему это надёжно.
5. Что сделать дальше.

## Требования к заголовкам

Заголовок должен быть конкретным.

Хорошо:

```text
Автоматизация въезда и выезда без постоянного участия охраны
```

Слабо:

```text
Современные решения для вашего бизнеса
```

## Требования к CTA

Кнопки и призывы должны быть понятны:

- Получить консультацию
- Обсудить объект
- Рассчитать проект
- Подобрать оборудование
- Отправить заявку

Избегать:

- Узнать больше, если непонятно о чём;
- Стартовать;
- Получить демо, если демо фактически не предусмотрено.

## Контентная ревизия сайта

Для будущей правки текстов нужно пройти сайт по таблице:

| Страница | Текущий текст | Проблема | Предложение | Приоритет |
|---|---|---|---|---|
| `/...` | ... | Англицизм / неясно / слабо | ... | P0/P1/P2 |

Приоритеты:

- P0 — мешает пониманию или доверию;
- P1 — желательно исправить в ближайшем пакете;
- P2 — косметика.

## Правила для следующих текстовых правок

После P0-русификации любые новые текстовые изменения нужно проводить отдельными пакетами:

1. **P0** — только то, что влияет на доверие, заявки, понятность оффера или ломает мобильную версию.
2. **P1** — улучшение продаж, SEO/GEO, структуры блоков, доверия, конкретики и отраслевой терминологии.
3. **P2** — косметика, уточнения, стилистическая полировка, второстепенные формулировки.

Запрещено смешивать в одном коммите:

- текстовую русификацию;
- SEO/GEO-изменения;
- мобильную вёрстку;
- изменение форм заявок;
- изменение маршрутов;
- изменение API;
- изменение структуры данных.

Исключение допустимо только для маленького follow-up, когда новая русская формулировка вызывает очевидное мобильное переполнение. В этом случае в коммите должно быть явно указано `fix(mobile)`.

## Правила мобильной проверки после русификации

Русские формулировки часто длиннее английских или смешанных терминов. Поэтому после любого изменения видимого текста нужно проверять мобильную версию.

Минимальный набор ширин:

- 360 px;
- 390 px;
- 400 px.

Минимальный набор проверок:

- нет горизонтального скролла;
- текст не обрезается справа;
- заголовки не уходят под шапку;
- карточки не становятся шире экрана;
- изображения имеют `max-w-full` / `w-full` там, где это требуется;
- формы остаются читаемыми;
- кнопки полностью видны и нажимаются;
- мобильное меню прокручивается, если пунктов больше высоты экрана.

Для P0-страниц после текстовых изменений проверять минимум:

- `/`;
- `/contacts`;
- `/quiz`;
- `/keysy`;
- один короткий объект, например `/keysy/amaks-otel-kazan`;
- один объект с длинным названием, например `/keysy/arktika`;
- `/resheniya/dlya-rukovoditeley`;
- `/resheniya/torgovye-centry`.

## Что нельзя менять без отдельного согласования

Следующие зоны считаются чувствительными и не должны попадать в обычную редакторскую правку:

- маршруты и URL;
- `metadata`;
- JSON-LD;
- FAQ-блоки;
- ExtendedInfo / расширенные SEO/GEO-блоки;
- формы заявок и API отправки;
- навигационная структура сайта;
- тексты, влияющие на юридические или коммерческие обязательства;
- обещания по точности распознавания, срокам реакции, стоимости и окупаемости.

Для этих зон требуется отдельная задача и согласование с архитектором сайта.

## Формат постановки задач агентам

Для командной работы с AI-агентами использовать шапку:

```text
FROM: <отправитель>
TO: <получатель>
TASK: <код задачи>
REF: <связанные задачи / ветки / теги>
STATUS: <статус>
```

Пример:

```text
FROM: Андрей / РОСПАРК
TO: РОСПАРК — технический редактор
TASK: EDITOR-P1-RU-SEO-001
REF: CONTENT-P0-RU-TEXT-001 / checkpoint-after-p0-ru-text-only-001
STATUS: ready-for-editor-review
```

Роли в редакционном цикле:

| Роль | Зона ответственности |
|---|---|
| Архитектор сайта | границы изменений, структура, риски, файлы, безопасное ТЗ разработчику |
| AI-маркетолог | оффер, польза для клиента, доверие, структура продаж, новости, статьи |
| Технический редактор | русский язык, терминология, ясность, стиль, отсутствие лишних англицизмов |
| Разработчик | безопасное внесение согласованных правок в код |

## Рекомендация для следующего этапа

Следующий крупный этап не должен быть продолжением P0-пакета. Его лучше оформить отдельной задачей, например:

```text
CONTENT-P1-RU-SEO-GEO-001 — редакционно-маркетинговая доработка P1-страниц и SEO/GEO-блоков
```

Цель следующего этапа:

- пройти оставшиеся иностранные и смешанные формулировки;
- не заменять термины механически;
- сохранить техническую точность;
- усилить доверие и конкретику;
- отдельно согласовать SEO/GEO-блоки перед изменением;
- после каждого пакета выполнять мобильную проверку.
