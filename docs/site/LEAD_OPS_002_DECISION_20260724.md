# РОСПАРК — decision packet `LEAD-OPS-002`

Дата аудита и решений: 2026-07-24

Статус: L1/L2/L3 реализованы локально за выключенными feature gates;
production smoke не начат

Граница: документ не разрешает deploy, реальные сообщения или выгрузку
персональных данных

## 1. Итог

На сайте существуют два технически независимых lead-контура, но ни один пока
не является полным операционным реестром.

| Контур | Что работает | Чего нет |
|---|---|---|
| Формы сайта → `POST /api/lead` | consent, валидация, attribution, доставка Email / Telegram / MAX, частичный успех | постоянный реестр, idempotency, статусы, ответственный, история обработки, retry outbox |
| Demo feedback → `POST /api/demo/feedback-leads` | отдельный consent, SQLite, 30-дневный TTL, idempotency одной session/request | уведомление менеджера, `assigned`, timestamps статусов, безопасный export, управляемая очистка, операционный интерфейс |

Email, Telegram и MAX сейчас являются только каналами уведомления. SQLite-
таблица demo feedback является техническим хранилищем, но не рабочим реестром
продаж.

До рекламного трафика нужен один источник истины и замкнутая цепочка:

```text
accepted
→ registered
→ notification queued
→ assigned
→ contacted
→ closed
```

## 2. Подтверждённое текущее состояние

### 2.1. Основные формы сайта

`app/api/lead/route.ts`:

- требует буквальное boolean-значение `consent: true`;
- принимает имя, телефон, коммерческий контекст и attribution;
- передаёт данные в `lib/leads.ts`;
- возвращает успех, если сработал минимум один настроенный канал;
- возвращает `500`, если все каналы недоступны;
- использует rate-limit в памяти процесса.

`lib/leads.ts`:

- отправляет уведомления в Email, Telegram и внутренний MAX;
- допускает частичный успех;
- записывает ошибки каналов только в server log;
- не сохраняет принятую заявку и результаты доставки в реестр;
- не создаёт retry-задачу после временной ошибки канала.

Следствие: при сбое всех каналов пользователь получает ошибку, но server-side
записи для повторной доставки нет. При успехе одного канала нет единой записи,
по которой можно подтвердить назначение, первый контакт и закрытие.

### 2.2. Demo feedback

`app/api/demo/feedback-leads/route.ts` и
`app/lib/demo-feedback-lead-store.ts`:

- требуют отдельный feedback consent;
- разрешают запись только для собственной не-seed demo-заявки;
- хранят нормализованный телефон, источник, канал share, consent version и
  срок удаления;
- предотвращают дубль по `session_ref + request_id`;
- не возвращают телефон в ответе API.

Фактически подтверждённый backup от 2026-07-23 содержал 7 строк
`demo_feedback_leads`. Это технические/QA-записи; они не подтверждают семь
реальных лидов.

### 2.3. Статусы и очистка

Текущая миграция разрешает только:

```text
new | contacted | closed
```

Roadmap требует:

```text
new → assigned → contacted → closed
```

При этом код не содержит ни одного `UPDATE demo_feedback_leads`: status всегда
остаётся `new`.

30-дневное удаление запускается только при следующем обращении к guest request
store или при создании нового feedback lead. Это opportunistic cleanup, а не
гарантированное удаление в момент истечения срока.

### 2.4. Дополнительный технический долг

- `lib/leads2.ts` не используется активным API и расходится с
  `lib/leads.ts`; удалять его до отдельной проверки истории нельзя, но он не
  должен считаться вторым действующим контрактом.
- автоматического теста status transitions, outbox и delivery retry нет;
- production smoke основного `/api/lead` требует реального сообщения и поэтому
  остаётся запрещён без отдельного согласования;
- политика и согласие описывают обработку обращений, технические данные и MAX,
  но перед включением конкретного внешнего мессенджера и утверждением сроков
  хранения нужен отдельный фактологический/юридический review.

## 3. Рекомендуемый источник истины

### Вариант A — существующая CRM

Выбирать, если у компании уже есть реально используемая CRM с:

- API или надёжным webhook;
- ответственными и ролями;
- статусами и журналом изменений;
- правилами дублей;
- резервным доступом;
- экспортом и удалением данных.

В этом случае сайт сохраняет заявку через CRM adapter, а Email/MAX остаются
уведомлениями.

### Вариант B — минимальный контролируемый реестр

Рекомендуемый промежуточный вариант, если готовой CRM нет.

Предлагаемый отдельный контур:

```text
/var/lib/rospark-leads/lead-registry.sqlite
```

Это только проектное предложение. Путь не создан и production не изменён.

Почему отдельный реестр:

- бизнес-лиды не смешиваются с временной demo-базой;
- checkout и `.next` не становятся местом постоянного хранения;
- backup, retention и права можно назначить отдельно;
- отложенный перенос demo SQLite не блокирует lead-операции.

Google Sheets, Email, Telegram и MAX не рекомендуются как источник истины:
они не обеспечивают надёжную idempotency, status history, контролируемый
доступ и гарантированную обработку дублей.

## 4. Минимальная целевая модель

### `lead_records`

- случайный `id`;
- `submission_id` / idempotency key;
- `kind`: `site_form` или `demo_feedback`;
- имя и контакт только в объёме, необходимом для связи;
- нормализованный телефон и отдельный hash для поиска дублей;
- source, intent, product, package, page и allowlisted attribution;
- consent version и timestamp;
- `status`: `new`, `assigned`, `contacted`, `closed`;
- `assigned_to`, `assigned_at`;
- `first_contact_at`;
- `closed_at`, `close_outcome`;
- `created_at`, `updated_at`, `expires_at`.

### `lead_status_events`

Append-only журнал:

```text
lead_id
from_status
to_status
actor
created_at
```

### `lead_notification_outbox`

- `lead_id`;
- канал;
- `pending | sent | failed`;
- количество попыток;
- время следующей попытки;
- время успешной доставки;
- безопасный error code без токенов и полного payload.

## 5. Требуемый порядок операции

```text
1. Validate + consent
2. Register lead in transaction
3. Create outbox rows
4. Return registered result
5. Worker sends notifications
6. Human assigns lead
7. Human records first contact
8. Human closes lead
```

Уведомление не должно предшествовать созданию записи. Временный сбой MAX,
Email или другого канала не должен уничтожать уже принятую заявку.

Для первой версии публичная admin-панель не требуется. Достаточен защищённый
операционный интерфейс или контролируемый export без ручного чтения
production SQLite. Конкретный способ зависит от решения о CRM.

## 6. Решения владельца

Ответы директора от 2026-07-24:

| ID | Решение | Статус |
|---|---|---|
| D1 | Источник истины | подтверждён отдельный реестр на VPS; CRM есть, но её API и интеграция пока не настроены |
| D2 | Владелец очереди | директор |
| D3 | Резервный ответственный | Сергей, РОП — руководитель отдела продаж |
| D4 | Рабочие часы и часовой пояс | понедельник–пятница, `10:00–18:00`, `Europe/Moscow` |
| D5 | Время первого контакта | подтверждён один рабочий час |
| D6 | Каналы уведомления | основной — MAX-группа отдела продаж; Email планируется как резервный, но пока не настроен |
| D7 | Срок хранения | обычный лид — 60 дней; demo feedback остаётся 30 дней |
| D8 | Правило дублей | подтверждено: одинаковый нормализованный телефон, открытый лид и окно 24 часа от последней заявки |
| D9 | Результаты закрытия | подтверждены: обработан, нет связи, нецелевой, дубль, тест |
| D10 | Экспорт и удаление | Андрей: полный admin, export и ручное удаление; Сергей, РОП: просмотр, обработка и export без удаления и без VPS/SSH |

SLA здесь означает внутреннее измеримое правило: между регистрацией лида и
первой подтверждённой попыткой связаться должно пройти не более одного
рабочего часа. Это не публичное обещание на сайте.

Пока Email не настроен и не проверен, у уведомлений есть только один
подтверждённый канал — MAX. Отказ MAX не должен приводить к потере лида:
registry остаётся источником истины, а outbox сохраняет неуспешную попытку.

Для кода используются стабильные outcome-коды:

| Код | Отображаемое значение |
|---|---|
| `processed` | обработан |
| `no_contact` | нет связи |
| `not_target` | нецелевой |
| `duplicate` | дубль |
| `test` | тест |

Production path выбран как `/var/lib/rospark-leads/lead-registry.sqlite`, но
каталог и файл на VPS ещё не созданы. Web-роли D10 реализованы локально в L3,
но feature gate выключен, production environment не менялся и учётные записи
на VPS не создавались.

## 7. Этапы после подтверждения оставшихся решений

### L1 — registry foundation — реализован локально

- добавлены отдельные таблицы `lead_records`, `lead_submissions` и
  `lead_status_events`;
- hard idempotency работает по `submission_id`;
- повтор по тому же телефону в течение 24 часов от последней заявки создаёт
  новую submission, привязанную к открытому lead record;
- после `closed` или за пределами 24 часов создаётся новый lead record;
- переходы ограничены цепочкой
  `new → assigned → contacted → closed`;
- обычный лид получает retention 60 дней, demo feedback — 30 дней;
- явная cleanup-функция удаляет истёкший lead и связанные submissions/events
  через cascade;
- локальный smoke проверяет миграцию, consent, idempotency conflict, дубли,
  переходы, outcomes и retention;
- production default path вынесен за Git checkout;
- реальной внешней отправки нет.

L1 подключается к `/api/lead` и `/api/demo/feedback-leads` только при
`LEAD_REGISTRY_ENABLED=true`. По умолчанию flag выключен, поэтому production
продолжает работать по прежнему контракту.

### L2 — transactional outbox — реализован локально

- оба API feature-gated подключены к registry;
- lead/submission и MAX/Email outbox создаются одной транзакцией;
- browser-формы сохраняют один `submissionId` для повторной отправки
  неизменённого payload;
- worker использует lease, retry/backoff и конечный `dead`;
- в outbox хранится только safe error code, без provider response и токенов;
- worker печатает только агрегированные счётчики без PII;
- реальные transport отключены `LEAD_OUTBOX_PROCESSING_ENABLED=false`;
- smoke использует только transport doubles.

Failure dashboard относится к L3 вместе с операционным интерфейсом.

Изолированный API-smoke дополнительно подтвердил регистрацию, idempotent retry,
`409` при конфликте ключа и атомарную pending MAX-запись. Worker оставался
выключен, внешних сообщений не было, временный SQLite удалён.

### L3 — операционная обработка — реализован локально

- добавлен защищённый `/admin/leads` и отдельный login;
- реализованы персональные роли `director` и `sales_head`;
- доступны поиск, фильтры, сводка статусов и состояния outbox;
- доступны назначение Андрею/Сергею, первый контакт, закрытие и outcome;
- контролируемый CSV export защищён от formula injection и ограничен 5000
  строками;
- ручное удаление требует директора, публичный ID и фиксированную причину;
- append-only audit фиксирует login/logout/list/export/status/delete без PII;
- admin route получает `noindex`, `no-store`, запрет iframe и `nosniff`;
- публичная Метрика, header, footer и cookie banner исключены из admin-контура;
- сессия подписывается HMAC, cookie — `HttpOnly` и `SameSite=Strict`;
- пароли сохраняются только как scrypt-хеши в server environment;
- изменяющие запросы защищены same-origin проверкой с учётом reverse proxy;
- login имеет локальный rate-limit `5 / 15 минут / IP`.

Подтверждённая матрица L3:

| Возможность | Андрей | Сергей, РОП |
|---|---:|---:|
| Просмотр и поиск | да | да |
| Назначение, контакт, закрытие | да | да |
| CSV export | да | да |
| Ручное удаление | да | нет |
| VPS/SSH | существующий доступ | нет |

Автоматический тест L3 проверяет password/session, матрицу ролей, workflow,
audit, CSV и удаление. Изолированный production-preview дополнительно
подтвердил:

- запрос login без Origin — `403`;
- login обеих ролей — `200`;
- list и CSV — `200`, CSV начинается с UTF-8 BOM;
- `new → assigned → contacted → closed` — три успешных операции;
- удаление Сергеем — `403`, удаление Андреем — `200`;
- audit сохраняет запись удаления после cascade удаления лида;
- `PRAGMA quick_check` — `ok`;
- desktop и mobile 390 px — без горизонтального переполнения;
- browser console — без ошибок;
- Метрика и публичные элементы сайта в admin-контуре отсутствуют.

Тестовая база и локальный listener удалены. Production, VPS, MAX и Email не
изменялись.

### L4 — согласованный production smoke

- отдельное окно;
- заранее назначенный получатель;
- одна явно маркированная `TEST`-заявка;
- проверка registry → outbox → notification → assigned → contacted → closed;
- удаление или закрытие тестовой записи;
- фиксация результата без публикации PII.

Production runbook, read-only preflight, systemd templates и rollback
подготовлены локально в
`docs/production/LEAD_OPS_L4_RUNBOOK_20260724.md`. Фактический VPS preflight
после L3 выполнен 2026-07-24: production остаётся на документированном SHA,
PM2 online, Node.js 22, MAX lead keys присутствуют, место есть; новый registry
и systemd units ещё не создавались. Документ не разрешает deploy или реальное
сообщение.

## 8. Критерий закрытия `LEAD-OPS-002`

- один источник истины;
- idempotent регистрация;
- уведомления через retry outbox;
- статусы `new → assigned → contacted → closed`;
- owner, backup и рабочие часы подтверждены;
- SLA измеряется по timestamps;
- retention и удаление проверяются автоматически;
- Email/MAX не подменяют реестр;
- аналитика получает только агрегированные события без PII;
- реальный production smoke выполнен только после отдельного подтверждения.

L1–L3 закрыты локально, ops-пакет L4 подготовлен. Полный `LEAD-OPS-002`
остаётся открытым до отдельно согласованного maintenance window и L4.
