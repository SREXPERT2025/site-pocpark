# РОСПАРК — decision packet `LEAD-OPS-002`

Дата аудита: 2026-07-24  
Статус: read-only аудит завершён; реализация и production smoke не начаты  
Граница: документ не назначает сотрудников, не устанавливает SLA и не
разрешает реальные сообщения или выгрузку персональных данных

## 1. Итог

На сайте существуют два технически независимых lead-контура, но ни один пока
не является полным операционным реестром.

| Контур | Что работает | Чего нет |
|---|---|---|
| Формы сайта → `POST /api/lead` | consent, валидация, attribution, доставка Email / Telegram / MAX, частичный успех | постоянный реестр, idempotency, статусы, ответственный, история обработки, retry outbox |
| Demo feedback → `POST /api/demo/feedback-leads` | отдельный consent, SQLite, 30-дневный TTL, idempotency одной session/request | уведомление менеджера, `assigned`, timestamps статусов, безопасный export, управляемая очистка, операционный интерфейс |

Email, Telegram и MAX сейчас являются только каналами уведомления. SQLite-
таблица demo feedback является техническим хранилищем, но не рабочим реестром
продаж.

До рекламного трафика нужен один источник истины и замкнутая цепочка:

```text
accepted
→ registered
→ notification queued
→ assigned
→ contacted
→ closed
```

## 2. Подтверждённое текущее состояние

### 2.1. Основные формы сайта

`app/api/lead/route.ts`:

- требует буквальное boolean-значение `consent: true`;
- принимает имя, телефон, коммерческий контекст и attribution;
- передаёт данные в `lib/leads.ts`;
- возвращает успех, если сработал минимум один настроенный канал;
- возвращает `500`, если все каналы недоступны;
- использует rate-limit в памяти процесса.

`lib/leads.ts`:

- отправляет уведомления в Email, Telegram и внутренний MAX;
- допускает частичный успех;
- записывает ошибки каналов только в server log;
- не сохраняет принятую заявку и результаты доставки в реестр;
- не создаёт retry-задачу после временной ошибки канала.

Следствие: при сбое всех каналов пользователь получает ошибку, но server-side
записи для повторной доставки нет. При успехе одного канала нет единой записи,
по которой можно подтвердить назначение, первый контакт и закрытие.

### 2.2. Demo feedback

`app/api/demo/feedback-leads/route.ts` и
`app/lib/demo-feedback-lead-store.ts`:

- требуют отдельный feedback consent;
- разрешают запись только для собственной не-seed demo-заявки;
- хранят нормализованный телефон, источник, канал share, consent version и
  срок удаления;
- предотвращают дубль по `session_ref + request_id`;
- не возвращают телефон в ответе API.

Фактически подтверждённый backup от 2026-07-23 содержал 7 строк
`demo_feedback_leads`. Это технические/QA-записи; они не подтверждают семь
реальных лидов.

### 2.3. Статусы и очистка

Текущая миграция разрешает только:

```text
new | contacted | closed
```

Roadmap требует:

```text
new → assigned → contacted → closed
```

При этом код не содержит ни одного `UPDATE demo_feedback_leads`: status всегда
остаётся `new`.

30-дневное удаление запускается только при следующем обращении к guest request
store или при создании нового feedback lead. Это opportunistic cleanup, а не
гарантированное удаление в момент истечения срока.

### 2.4. Дополнительный технический долг

- `lib/leads2.ts` не используется активным API и расходится с
  `lib/leads.ts`; удалять его до отдельной проверки истории нельзя, но он не
  должен считаться вторым действующим контрактом.
- автоматического теста status transitions, outbox и delivery retry нет;
- production smoke основного `/api/lead` требует реального сообщения и поэтому
  остаётся запрещён без отдельного согласования;
- политика и согласие описывают обработку обращений, технические данные и MAX,
  но перед включением конкретного внешнего мессенджера и утверждением сроков
  хранения нужен отдельный фактологический/юридический review.

## 3. Рекомендуемый источник истины

### Вариант A — существующая CRM

Выбирать, если у компании уже есть реально используемая CRM с:

- API или надёжным webhook;
- ответственными и ролями;
- статусами и журналом изменений;
- правилами дублей;
- резервным доступом;
- экспортом и удалением данных.

В этом случае сайт сохраняет заявку через CRM adapter, а Email/MAX остаются
уведомлениями.

### Вариант B — минимальный контролируемый реестр

Рекомендуемый промежуточный вариант, если готовой CRM нет.

Предлагаемый отдельный контур:

```text
/var/lib/rospark-leads/lead-registry.sqlite
```

Это только проектное предложение. Путь не создан и production не изменён.

Почему отдельный реестр:

- бизнес-лиды не смешиваются с временной demo-базой;
- checkout и `.next` не становятся местом постоянного хранения;
- backup, retention и права можно назначить отдельно;
- отложенный перенос demo SQLite не блокирует lead-операции.

Google Sheets, Email, Telegram и MAX не рекомендуются как источник истины:
они не обеспечивают надёжную idempotency, status history, контролируемый
доступ и гарантированную обработку дублей.

## 4. Минимальная целевая модель

### `lead_records`

- случайный `id`;
- `submission_id` / idempotency key;
- `kind`: `site_form` или `demo_feedback`;
- имя и контакт только в объёме, необходимом для связи;
- нормализованный телефон и отдельный hash для поиска дублей;
- source, intent, product, package, page и allowlisted attribution;
- consent version и timestamp;
- `status`: `new`, `assigned`, `contacted`, `closed`;
- `assigned_to`, `assigned_at`;
- `first_contact_at`;
- `closed_at`, `close_outcome`;
- `created_at`, `updated_at`, `expires_at`.

### `lead_status_events`

Append-only журнал:

```text
lead_id
from_status
to_status
actor
created_at
```

### `lead_notification_outbox`

- `lead_id`;
- канал;
- `pending | sent | failed`;
- количество попыток;
- время следующей попытки;
- время успешной доставки;
- безопасный error code без токенов и полного payload.

## 5. Требуемый порядок операции

```text
1. Validate + consent
2. Register lead in transaction
3. Create outbox rows
4. Return registered result
5. Worker sends notifications
6. Human assigns lead
7. Human records first contact
8. Human closes lead
```

Уведомление не должно предшествовать созданию записи. Временный сбой MAX,
Email или другого канала не должен уничтожать уже принятую заявку.

Для первой версии публичная admin-панель не требуется. Достаточен защищённый
операционный интерфейс или контролируемый export без ручного чтения
production SQLite. Конкретный способ зависит от решения о CRM.

## 6. Решения владельца

Без этих ответов реализация не начинается:

| ID | Решение | Рекомендуемый default |
|---|---|---|
| D1 | Есть ли действующая CRM с доступным API? | если нет — минимальный отдельный реестр |
| D2 | Владелец очереди | конкретная роль и сотрудник |
| D3 | Резервный ответственный | сотрудник, реально имеющий доступ |
| D4 | Рабочие часы и часовой пояс | зафиксировать фактический режим |
| D5 | Время первого контакта | выбрать измеримый срок в рабочих часах |
| D6 | Основной и резервный канал уведомления | один primary и один fallback |
| D7 | Срок хранения обычного лида | согласовать отдельно от 30-дневного demo feedback |
| D8 | Правило дублей | телефон + временное окно + ручное объединение |
| D9 | Допустимые результаты закрытия | согласованный короткий справочник |
| D10 | Кто может экспортировать/удалять данные | минимальный список ролей |

Рекомендуемый рабочий SLA для обсуждения — первый контакт в течение одного
рабочего часа. Это не утверждённое обязательство и не публичное обещание.

## 7. Этапы после подтверждения решений

### L1 — registry foundation

- новая изолированная схема;
- idempotent create;
- status transitions;
- consent/retention contract;
- unit и integration tests;
- никакой реальной внешней отправки.

### L2 — transactional outbox

- Email/MAX adapters;
- retry/backoff;
- безопасные логи;
- failure dashboard;
- тестовые transport doubles.

### L3 — операционная обработка

- назначение ответственного;
- первый контакт;
- закрытие и outcome;
- контролируемый export или CRM sync;
- аудит доступа и удаления.

### L4 — согласованный production smoke

- отдельное окно;
- заранее назначенный получатель;
- одна явно маркированная `TEST`-заявка;
- проверка registry → outbox → notification → assigned → contacted → closed;
- удаление или закрытие тестовой записи;
- фиксация результата без публикации PII.

## 8. Критерий закрытия `LEAD-OPS-002`

- один источник истины;
- idempotent регистрация;
- уведомления через retry outbox;
- статусы `new → assigned → contacted → closed`;
- owner, backup и рабочие часы подтверждены;
- SLA измеряется по timestamps;
- retention и удаление проверяются автоматически;
- Email/MAX не подменяют реестр;
- аналитика получает только агрегированные события без PII;
- реальный production smoke выполнен только после отдельного подтверждения.
