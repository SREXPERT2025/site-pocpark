## 1. Как проводился аудит

Аудит собран из четырех независимых проверок субагентов и контрольной сверки по коду:

- SEO/GEO и контентная архитектура;
- UX/UI, мобильный опыт и конверсионный маршрут;
- technical/performance/a11y;
- B2B-маркетинг, воронка и качество лидов.

Проверялись:

- `app/` - страницы, layout, навигация, формы, API;
- `content/` - статьи, возможности, оборудование, кейсы;
- `public/` - документы, изображения, видео;
- `docs/site/` - существующие планы и структура.

Текущая база сайта уже сильная: есть коммерческие страницы решений, каталог оборудования, 30 кейсов, 6 страниц возможностей, 5 статей, sitemap, JSON-LD для части разделов, HTTPS-preview и визуальная подача. Главная проблема теперь не в количестве страниц, а в согласованности воронки, доверии, технической надежности и SEO-хабах.

## 2. Главные выводы

### 2.1. Самый высокий приоритет - заявки и контекст лида

Сайт уже приводит пользователя к CTA, но часть важного контекста теряется:

- `LeadForm` отправляет `comment`, а API читает `message`;
- `/quiz?source=...` меняет заголовок на странице, но не передает `source`, `intent`, `product` и фактический URL в заявку;
- карточки оборудования ведут в квиз с `product=...`, но квиз не добавляет этот продукт в payload;
- delivery заявок может вернуть success даже при неочевидных проблемах доставки.

Это влияет не на внешний вид сайта, а на качество заявок и работу продаж.

### 2.2. Второй приоритет - единый конверсионный маршрут

Одни и те же CTA иногда ведут в разные сценарии:

- desktop CTA в шапке ведет на `/quiz?source=kp`;
- mobile CTA с тем же смыслом ведет на `/contacts`;
- некоторые нижние CTA на страницах решений снова ведут в общий `/quiz` без контекста страницы;
- `/quiz` по тексту обещает расчет/КП/несколько вопросов, но фактически является короткой формой.

Нужно выбрать модель:

1. либо квиз становится настоящей квалификацией;
2. либо переименовывается в простую заявку на расчет.

Рекомендуемое решение: сделать настоящий легкий квалификационный квиз на 4-6 вопросов.

### 2.3. SEO/GEO точка роста - хабы и внутренняя сетка

Сейчас есть хорошие дочерние страницы, но не все хабы работают как посадочные:

- нет полноценной страницы `/resheniya`;
- `/vozmozhnosti` слабее дочерних страниц: мало явных ссылок, нет Breadcrumb/ItemList JSON-LD;
- в меню "Возможности" нет `/vozmozhnosti/onlain-oplata` и `/vozmozhnosti/raspoznavanie-nomerov`;
- статьи уже полезны, но их пока всего 5;
- кейсы есть в количестве, но многие требуют усиления по структуре и GEO-фактам.

### 2.4. Technical/a11y точка роста - базовая надежность

Критичные технические направления:

- delivery policy для `/api/lead`;
- один корректный `<main>` на документ;
- keyboard-доступность меню;
- a11y форм: `id/htmlFor`, `aria-live`, `required`, `inputMode`;
- тяжелые изображения/видео;
- lint-gate сейчас фактически не настроен;
- markdown рендерится через `dangerouslySetInnerHTML` без санитайза.

## 3. P0 - исправить в первую очередь

### P0.1. Починить payload обычных форм

Файлы:

- `app/components/forms/LeadForm.tsx`
- `app/api/lead/route.ts`
- `lib/leads.ts`

Проблема:

- форма отправляет поле `comment`;
- API читает только `message`;
- вводные пользователя могут не попадать в заявку.

Решение:

- в API принимать оба поля: `message` и `comment`;
- в payload привести к единому `message`;
- в `formatLeadText` выводить сообщение;
- добавить минимальную проверку ручным POST/smoke.

Проверки:

- `npm run typecheck`;
- `npm run build`;
- ручной POST в `/api/lead` с `comment`.

### P0.2. Починить delivery policy заявок

Файлы:

- `lib/leads.ts`
- `app/api/lead/route.ts`
- `.env.example` или docs, если есть/будет добавлен

Проблема:

- если каналы доставки не настроены, `sendLead` может завершиться без явного fail;
- Telegram `fetch` не проверяет `res.ok`;
- MAX-ошибка логируется, но не влияет на результат;
- 500 может вернуть клиенту сырой текст ошибки.

Решение:

- определить хотя бы один обязательный канал доставки;
- проверять `res.ok` у Telegram;
- собирать результаты доставки по каналам;
- возвращать success только если хотя бы один канал реально принял заявку;
- клиенту отдавать общий текст ошибки, детали - только в server log.

### P0.3. Передавать `source`, `intent`, `product` из квиза

Файлы:

- `app/(narrow)/quiz/page.tsx`
- `app/components/forms/QuizForm.tsx`
- `app/(narrow)/oborudovanie/[slug]/ProductView.tsx`
- `app/api/lead/route.ts`
- `lib/leads.ts`

Проблема:

- `/quiz?source=kp`, `/quiz?source=warehouse`, `/quiz?product=...` меняют контекст входа, но заявка получает только `sourceSection: quiz` и `sourcePage: /quiz`.

Решение:

- читать search params в quiz page/client wrapper;
- передавать в `QuizForm`;
- отправлять `source`, `intent`, `product`, `sourceUrl`;
- выводить это в тексте заявки.

### P0.4. Унифицировать CTA в шапке mobile/desktop

Файлы:

- `app/components/layout/Header.tsx`
- `app/components/layout/MobileMenu.tsx`

Проблема:

- одинаковый CTA "Получить коммерческое предложение" ведет в разные места.

Решение:

- mobile и desktop CTA вести на `/quiz?source=kp`;
- телефон и контакты оставить отдельными действиями.

### P0.5. Проверить и исправить CTA из markdown

Файлы:

- `lib/content-parser.ts`
- `content/vozmozhnosti/*.md`
- `content/resheniya/kak-my-rabotaem.md`

Проблема:

- в контенте CTA часто задан как `title`, а парсер ожидает `label`;
- часть CTA может рендериться некорректно или без заголовка.

Решение:

- поддержать оба поля в парсере: `label ?? title`;
- постепенно привести frontmatter к единому формату.

### P0.6. Найти и закрыть битые PDF-ссылки оборудования

Файлы:

- `content/oborudovanie/*.md`
- `public/docs/`

Проблема:

- markdown ссылается на паспорта/схемы, которых нет в `public/docs`.

Решение:

- составить список битых ссылок;
- удалить/заменить ссылки или добавить реальные PDF;
- не оставлять кнопки скачивания на 404.

## 8. Рабочий протокол

- Делать по одной логической задаче за раз.
- После каждого этапа: `npm run typecheck`, `npm run build`, `git diff --check`.
- Для изменений форм/API делать отдельный smoke.
- Не менять production без явного подтверждения.
- Коммитить завершенные этапы маленькими понятными коммитами.
- Не запускать тяжелую генерацию изображений, если снова появляются transport disconnect.
