# РОСПАРК — сценарий коммерческого показа Demo Release v1

Дата: 2026-07-23
Задача: `DEMO-GROWTH-001`
Статус: внутренний сценарий показа; не является инструкцией production-системы

## 1. Цель показа

За 5–8 минут показать не отдельные экраны, а связанный рабочий процесс:

```text
арендатор создаёт гостевую заявку
→ гость получает ссылку и QR-код
→ арендатор оплачивает парковку посетителя
→ владелец видит операции и отчётность
```

Показ должен помочь заказчику понять роли, последовательность действий и
состав программной части. Он не заменяет обследование объекта, расчёт,
техническое задание или интеграционный проект.

## 2. Обязательная рамка перед началом

Менеджер проговаривает:

> Это интерактивная демонстрация интерфейса РОСПАРК на вымышленных данных.
> Она не управляет реальным шлагбаумом и не выполняет реальные списания.
> Состав ролей, интеграций и правил для вашего объекта определяется после
> обследования.

Не обещать:

- готовность конкретной интеграции без проверки;
- точный срок внедрения;
- цену;
- гарантированный процент распознавания;
- совместимость с оборудованием заказчика без аудита;
- полное совпадение demo и будущего production-интерфейса.

## 3. Подготовка

1. Открыть `/demo`.
2. Убедиться, что три карточки сценариев доступны.
3. Использовать только demo-доступ `TEST / TEST`.
4. Не вводить реальные персональные данные.
5. Для новой заявки использовать вымышленные имя, телефон и номер автомобиля.
6. Не включать согласие на обратную связь, если показ не предполагает
   контролируемое тестирование lead.
7. После показа выйти из demo-кабинета.

## 4. Сценарий показа

### Шаг 1. Общая карта — 30–60 секунд

URL: `/demo`

Показать:

- три роли;
- общий demo-вход;
- связанную последовательность;
- предупреждение о синтетических данных.

Фраза менеджера:

> Начнём с пути арендатора, затем покажем оплату парковки гостя и закончим
> сводкой владельца. Так видна не отдельная функция, а единая операционная
> цепочка.

### Шаг 2. Гостевая заявка — 2 минуты

URL: `/demo/gostevaya-zayavka`

Действия:

1. Войти с `TEST / TEST`.
2. Показать журнал и статусы существующих заявок.
3. Создать одну новую заявку на вымышленных данных.
4. Открыть карточку.
5. Показать публичную ссылку и QR-код.
6. Объяснить, что отменить можно только ожидающую заявку.
7. Показать copy/share-варианты, не выполняя реальную отправку без отдельной
   необходимости.

Акцент:

- заявка создаётся арендатором без звонка на пост охраны;
- срок действия и тип заявки задаются явно;
- действия сохраняются в demo-журнале;
- demo-данные изолированы от других browser-сессий.

### Шаг 3. Оплата парковки гостей — 1–2 минуты

URL: `/demo/web-skidki`

Действия:

1. Войти с `TEST / TEST`.
2. Выбрать активного синтетического посетителя или выполнить поиск.
3. Показать текущую стоимость и данные сессии.
4. Открыть подтверждение.
5. Применить demo-операцию.
6. Показать результат и историю.

Акцент:

- арендатор работает с уже существующей парковочной сессией;
- действие требует подтверждения;
- повторная или недопустимая операция не маскируется под успех;
- реальные деньги не списываются.

### Шаг 4. Кабинет владельца — 2 минуты

URL: `/demo/vladelec-parkovki`

Действия:

1. Войти с `TEST / TEST`.
2. Показать сводку за предыдущий период.
3. Переключить период.
4. Открыть раздел арендаторов и одну детализацию.
5. Показать гостевые заявки, оплаты и общий журнал операций.
6. Вернуться в сводку.

Акцент:

- владелец видит агрегированную картину и детализацию;
- заявки, оплаты и операции рассматриваются в одном контуре;
- текущий и исторический периоды разделены;
- данные demo являются детерминированными и синтетическими.

## 5. Завершение показа

Задать три вопроса:

1. Какая роль для объекта важнее в первую очередь: арендатор, служба
   эксплуатации или владелец?
2. Какие текущие действия выполняются вручную?
3. С какими системами и оборудованием потребуется обмен данными?

Следующее действие:

- при общем интересе — перейти к `/quiz` и собрать вводные;
- при техническом вопросе — назначить отдельную консультацию;
- при вопросе об интеграции — сначала зафиксировать систему, протокол,
  владельца данных и границы ответственности;
- не обещать оценку до получения достаточных исходных данных.

## 6. Короткие описания ролей

### Арендатор

Создаёт временный доступ для гостя, управляет ожидающими заявками и передаёт
гостю публичную ссылку или QR-код.

### Сотрудник арендатора, отвечающий за парковку гостя

Находит активную парковочную сессию посетителя и подтверждает её оплату за
счёт арендатора в рамках разрешённого сценария.

### Владелец парковки

Контролирует сводные показатели, арендаторов, гостевые заявки, оплаты и журнал
операций за выбранный период.

## 7. Что фиксировать после разговора

Без персональных данных в свободной аналитике:

```text
тип объекта
интересующая роль
интересующий сценарий
текущий ручной процесс
нужные интеграции
следующее согласованное действие
ответственный менеджер
дата следующего контакта
```

Контактные данные и содержание заявки передаются только через согласованный
lead-контур с явным согласием.
