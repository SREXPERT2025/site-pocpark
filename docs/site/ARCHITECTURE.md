# РОСПАРК — техническая архитектура сайта

Статус: рабочая документация v1  
Дата: 2026-05-03  
Проект: `rospark-frontend`

## Назначение документа

Документ описывает техническое устройство сайта РОСПАРК на уровне, достаточном для поддержки, безопасных правок, деплоя и постановки задач ИИ-агентам.

## Стек

- Next.js 14.2.x
- App Router
- TypeScript
- React
- Tailwind CSS
- Node.js
- PM2 на демо-сервере
- GitHub как основной источник кода

## Общая модель проекта

Сайт является коммерческим B2B-сайтом компании РОСПАРК. Он совмещает:

- лендинг;
- страницы решений по ролям и отраслям;
- каталог оборудования;
- карточки объектов;
- страницы возможностей;
- формы заявок;
- квиз;
- SEO/GEO-контент.

## Основные директории

| Директория | Назначение |
|---|---|
| `app/` | Маршруты Next.js App Router и часть компонентов |
| `app/(narrow)/` | Страницы с узким layout |
| `app/components/` | Компоненты, используемые страницами приложения |
| `components/` | Общие UI-компоненты, если используются вне `app/components` |
| `config/` | Конфигурационные данные проекта |
| `content/` | Контентные данные, тексты, карточки, структуры |
| `lib/` | Вспомогательная логика |
| `public/` | Статические файлы: изображения, иконки, ассеты |
| `docs/` | Документация проекта |

## Важные архитектурные правила

### 1. Мобильная версия — критичная часть продукта

Сайт часто смотрят с телефона. Любая новая секция должна сразу проектироваться под мобильные ширины 375–430 px.

Запрещено добавлять блоки, которые заведомо требуют ширину больше экрана без адаптации.

### 2. Коммерческий смысл важнее декоративности

На каждой странице пользователь должен быстро понять:

- какую проблему решает РОСПАРК;
- для кого это решение;
- что входит в систему;
- как оставить заявку;
- почему компании можно доверять.

### 3. Формы нельзя менять без проверки API

Формы связаны с маршрутом `/api/lead` и, возможно, с внешними каналами отправки. После изменений форм нужно проверять:

- успешную отправку;
- валидацию;
- отображение ошибок;
- работу на мобильном экране;
- получение заявки на нужные каналы.

### 4. Контент должен быть понятным российскому B2B-заказчику

Предпочтение — инженерный русский язык. Англицизмы использовать только там, где они действительно привычны и полезны.

### 5. SEO/GEO не должно ломать основной лендинг

Расширенный контент для поисковых систем и ИИ-поиска должен быть структурированно отделён от первого экрана и коммерческого сценария. Главная страница не должна превращаться в длинную техническую энциклопедию без приоритетов.

## Проверка перед commit

Минимальный набор:

```bash
npm run build
```

После мобильных или layout-правок дополнительно вручную проверить страницы из `docs/site/SITE_STRUCTURE.md`.

## Проверка перед деплоем

1. Убедиться, что локальная ветка `main` актуальна.
2. Выполнить `npm run build`.
3. Проверить ключевые страницы локально.
4. Сделать commit и tag/checkpoint при крупном изменении.
5. Запушить `main`.
6. На демо-сервере сделать backup.
7. На демо-сервере выполнить `git pull --ff-only origin main`.
8. Собрать проект.
9. Перезапустить PM2-процесс сайта.
10. Проверить сайт с телефона.

## Текущий production-процесс

На демо-сервере сайт работает под PM2-процессом `site-pocpark`. Рядом также может работать процесс `max-bot` для интеграции с MAX.

Перед любыми изменениями на сервере нужно смотреть:

```powershell
pm2 list
cd C:\site-pocpark
git status
```

## Неочевидные риски

- В корне сервера могут быть untracked-файлы, не относящиеся к проекту.
- Нельзя бездумно выполнять `git clean -fd`, пока не проверен список удаления через `git clean -nd`.
- Папка `node_modules` не должна попадать в commit.
- Локальные backup-файлы и архивы не должны попадать в commit.
- После изменения `.env.local` на сервере обычно нужен перезапуск PM2, а иногда и новая сборка, если переменная используется на этапе build.
