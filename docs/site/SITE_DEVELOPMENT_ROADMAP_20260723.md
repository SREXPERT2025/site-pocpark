## 2. Главные расхождения и риски

### Отложено. PROD-DATA-OPS — вынести SQLite из Git checkout

Статус: перенос отложен по решению владельца от 2026-07-23. Локальный аудит,
read-only VPS preflight и свежий проверенный online backup завершены; план
подготовлен в `docs/production/PROD_DATA_OPS_PLAN_20260723.md`. Текущая база
остаётся на старом пути, maintenance window не выполнялось.

Текущая production-база находится в:

```text
/var/www/rospark-site/.data/guest-requests.sqlite
```

Целевой каталог:

```text
/var/lib/rospark-demo/guest-requests.sqlite
```

Перенос выполнять отдельным окном:

- определить фактического process user;
- создать SQLite `.backup`;
- проверить `integrity_check` и `foreign_key_check`;
- остановить запись на время переключения;
- перенести базу с учётом WAL/SHM;
- обновить `DEMO_REQUESTS_DB_PATH`;
- проверить права и владельца;
- выполнить полный smoke;
- сохранить rollback.

Обычное копирование работающей SQLite/WAL не считается безопасным переносом.

Вернуть задачу в активный план перед заменой production checkout, изменением
deploy-схемы или следующим крупным production-релизом.

### P0. RUNTIME-001 — обязательный Node.js 22

Проект закреплён на Node.js 22 через `engines` и `.nvmrc`. Локальный запуск под
Node.js 26 воспроизвёл `500` в demo API при обращении к нативному
`better-sqlite3`; под Node.js 22 те же Stage B/Stage C тесты прошли.

Нужно:

- добавить проверку `node --version` в каждый preflight;
- не запускать build/start при несовпадении major-версии;
- документировать rebuild нативного модуля после смены Node ABI;
- использовать одинаковую версию Node для `npm ci`, build и runtime.

### P0. LEAD-OPS-002 — замкнуть обработку demo-лида

Сейчас consented feedback lead сохраняется в `demo_feedback_leads`, но
операционная обработка не замкнута.

Read-only аудит 2026-07-24 подтвердил два несвязанных контура:

- `/api/lead` доставляет Email / Telegram / MAX, но не сохраняет операционный
  реестр;
- `/api/demo/feedback-leads` сохраняет запись на 30 дней, но не создаёт
  outbox, не уведомляет менеджера и не меняет status;
- schema не содержит `assigned`, хотя этот переход записан в roadmap;
- очистка истёкших feedback leads выполняется opportunistically при следующей
  demo-операции, а не отдельным гарантированным job.

Decision packet:
`docs/site/LEAD_OPS_002_DECISION_20260724.md`.

Нужно:

- определить источник истины: CRM или контролируемый реестр;
- назначить владельца и резервного ответственного;
- добавить безопасный outbox/экспорт;
- уведомлять менеджера только после реального успешного действия;
- вести статусы `new → assigned → contacted → closed`;
- зафиксировать SLA первого контакта;
- проверить удаление по истечении срока хранения;
- исключить ручное чтение production SQLite как постоянный процесс.

Это решение означает принятие временного технического риска, а не отсутствие
риска. Публичная доступность сайта сама по себе создаёт поверхность атаки,
независимо от активности конкурентов и текущего объёма посетителей.

Этап нужно вернуть раньше в план при любом из условий:

- начинается активное продвижение или заметно растёт публичный трафик;
- расширяются формы, API, AI-виджет или внешние интеграции;
- появляется security-инцидент или новая critical-уязвимость;
- меняется production runtime;
- планируется крупный production-релиз.

Зафиксированный объём этапа:

1. создать отдельную upgrade-ветку;
2. выбрать поддерживаемую исправленную версию Next.js после проверки
   совместимости, а не обновлять production напрямую;
3. обновить Nodemailer, Sharp и транзитивные зависимости;
4. повторить typecheck, lint, production build и dependency audit;
5. проверить все 100 build-маршрутов;
6. повторить Stage B и Stage C demo-smoke;
7. провести desktop/mobile/a11y-приёмку трёх demo-сценариев;
8. провести повторный security audit;
9. выпускать только отдельным Release 2 с rollback-планом.

Исходная фиксация на 2026-07-23: `npm audit --omit=dev` показывал пять
production-зависимостей уровня high, включая прямые `next`, `nodemailer` и
`sharp`, а также транзитивные `postcss` и `js-yaml`.

Критерий готовности: нет неисследованных high/critical production findings,
все функциональные и визуальные проверки пройдены на Node.js 22.

## 11. Рабочий протокол

- один логический блок — один понятный diff;
- UI-блок — localhost desktop/mobile и подтверждение;
- код — typecheck, lint, build, `git diff --check` и целевой smoke;
- нативные модули — только под Node.js 22;
- контент — `draft → review → preview → approval → publication`;
- публичные факты — только из claim ledger;
- production, секреты, реальные сообщения и персональные данные — только по
  отдельному подтверждению;
- успешный локальный тест не равен production-ready;
- техническая готовность к индексации не равна гарантированным позициям.
