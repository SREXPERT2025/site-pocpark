# РОСПАРК — структура субагентов сайта

Статус: рабочая версия v1
Дата: 2026-07-06

## 1. Что создано

В проекте есть два уровня AI-команды:

1. Основной Codex — работает как Архитектор сайта РОСПАРК и отвечает за финальное решение.
2. Project-scoped субагенты в `.codex/agents` — помогают с узкими review и ТЗ, по умолчанию работают read-only.

Новые профильные субагенты:

- `rospark_ai_architect` — read-only профиль Архитектора/Оркестратора: scope, risks, task briefs, QA-gate.
- `rospark_ai_marketer` — маркетинг, офферы, SEO/GEO-смысл, статьи, новости.
- `rospark_tech_editor` — русский технический B2B-текст и безопасные формулировки.
- `rospark_ai_designer` — визуальная иерархия, CTA, доверие, мобильная подача.
- `rospark_frontend_coder` — read-only планирование фронтенд-правок, file-scope, проверки, откат.
- `rospark_qa_tester` — QA-проверка, сборка, мобильная версия, формы, merge-readiness.

Основной регламент:

- `docs/agents/AI_TEAM_ORCHESTRATION.md`

Существующие подробные базы знаний:

- `docs/agents/ROSPARK_SITE_ARCHITECT_GPT_INSTRUCTIONS.md`
- `docs/agents/ai-marketer/ROSPARK_AI_MARKETER_GPT.md`

## 2. Почему субагенты read-only

Главное правило: сайт не ломаем.

Постоянные субагенты должны помогать анализировать, критиковать, готовить безопасные задания и проверять риски. Они не должны самостоятельно менять файлы, делать commit, push, merge или deploy.

Каждый профиль обязан иметь:

- mission / роль;
- allowed actions;
- forbidden actions;
- read-only правило;
- input/output contract;
- формат отчета;
- условия эскалации Архитектору;
- запрет на выдумывание фактов, характеристик, сертификатов, цен и гарантий.

Кодовые изменения выполняются отдельно:

1. Архитектор утверждает scope.
2. Создается отдельная ветка от `ai-site-dev`.
3. Основной Codex или отдельный worker меняет только разрешенные файлы.
4. QA проверяет.
5. Андрей получает результат на визуальную проверку.

## 3. Типовой запуск команды

Пример задачи:

```text
Нужно понять, что улучшить по сайту для SEO/GEO.
Запусти read-only анализ ролями:
- rospark_ai_marketer
- rospark_tech_editor
- rospark_ai_designer
- rospark_qa_tester

Код не менять. Main, production, формы, API, маршруты, metadata и JSON-LD не трогать.
Верни общий план P0/P1/P2 и первый безопасный пул задач.
```

## 3.1. Production-ready цикл

Короткая схема:

1. Андрей ставит задачу.
2. Архитектор фиксирует цель, ветку, статус Git и forbidden-зоны.
3. Архитектор запускает нужных read-only субагентов.
4. Субагенты возвращают findings и safe next tasks.
5. Архитектор собирает единое решение.
6. Андрей/Архитектор утверждает scope.
7. Создается отдельная ветка от `ai-site-dev`.
8. Основной Codex или worker меняет только разрешенные файлы.
9. Выполняются diff и проверки.
10. QA дает вердикт.
11. Архитектор делает review.
12. Только потом commit и возможный merge в `ai-site-dev`.

`main`, push, merge в production-ветку и deploy — только отдельным прямым разрешением.

## 4. Передача в разработку

Когда план согласован, Архитектор формирует отдельный task для frontend-разработчика:

```text
FROM: РОСПАРК — Архитектор сайта
TO: РОСПАРК — Frontend-разработчик
TASK: DEV-<код>
STATUS: ready-for-dev

Ветка:
feature/site-YYYYMMDD-short-task-name

Можно менять:
- <точный файл>

Нельзя менять:
- формы и API заявок;
- маршруты;
- metadata;
- JSON-LD;
- sitemap/robots;
- env;
- unrelated-файлы.

Требуется:
1. ...
2. ...

Проверки:
- git status --short
- git diff --name-only
- npm run build
- мобильные ширины 360, 375, 390, 400, 430 px
```

## 5. GitHub-порядок

Все улучшения идут через отдельные ветки:

1. `ai-site-dev` — база для AI-разработки.
2. `feature/site-YYYYMMDD-*`, `fix/site-YYYYMMDD-*`, `content/site-YYYYMMDD-*` — одна ветка на один пул задач.
3. Проверка, commit, review.
4. Merge в `ai-site-dev` после подтверждения.
5. Новый пул задач — новая ветка.
6. `main` и production deploy — только после отдельного прямого разрешения Андрея.

## 6. Минимальный чек-лист безопасности

Перед любыми правками:

- текущая ветка не `main`;
- рабочее дерево понятно по `git status --short`;
- есть отдельная ветка под пул задач;
- перечислены файлы, которые можно менять;
- перечислены файлы, которые нельзя менять;
- известен план отката.

После правок:

- diff содержит только ожидаемые файлы;
- build прошел или причина пропуска указана;
- мобильная версия проверена, если менялся видимый интерфейс;
- формы, API, маршруты, SEO/GEO и production не затронуты случайно;
- QA-вердикт зафиксирован;
- Андрей получает результат на визуальную проверку.

## 7. Guardrails РОСПАРК

Запрещено без отдельного подтверждения:

- публиковать цены на отдельные элементы и оборудование;
- выдумывать технические характеристики, сертификаты, ГОСТы, гарантию, ресурс циклов;
- обещать 100% распознавание номеров, абсолютную безотказность или гарантированный рост заявок;
- менять формы, API, маршруты, metadata, JSON-LD, sitemap, robots;
- менять юридические данные, адреса, email и телефоны без подтверждения.

Публичные страницы пишутся в B2B-стиле: конкретно, технически, по-русски, без маркетинговой воды.
