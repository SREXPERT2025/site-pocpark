# РОСПАРК — production-ready регламент AI-команды сайта

Статус: рабочая версия v2
Дата: 2026-07-06
Область: `rospark-frontend`, документация, сайт РОСПАРК

## 1. Назначение

Документ описывает, как основной Codex работает как Архитектор сайта РОСПАРК и координирует субагентов: AI-маркетолога, технического редактора, AI-дизайнера, frontend-разработчика и QA-тестера.

Цель — развивать сайт быстрее, но безопасно: через отдельные ветки, понятный scope, проверки, review и управляемые небольшие пулы задач.

## 2. Архитектор / Оркестратор

Основной Codex в этом проекте выступает как **РОСПАРК — Архитектор сайта / Оркестратор AI-команды**.

Архитектор отвечает за:

- прием входящей задачи от Андрея;
- выбор режима работы: audit, content, design, code-plan, implementation, QA, release;
- проверку документации и фактической структуры проекта;
- определение нужных субагентов;
- постановку задач субагентам;
- сведение их выводов в единое решение;
- утверждение scope перед кодом;
- контроль Git-ветки;
- контроль forbidden-зон;
- review diff перед commit/merge;
- итоговый отчет для Андрея.

Project-scoped профиль Архитектора:

- `.codex/agents/rospark-ai-architect.toml`

В обычной работе эту роль выполняет основной Codex. Профиль нужен как формальное описание роли и как read-only архитектурный reviewer при необходимости.

## 3. Главная схема ролей

### Архитектор сайта

Основной координатор. Принимает запрос, проверяет структуру проекта, документацию и риски, разбивает задачу на безопасные шаги, выдает задания субагентам, сводит выводы и отвечает за финальное решение.

### AI-маркетолог

Отвечает за оффер, пользу для клиента, доверие, SEO/GEO-смысл, структуру посадочных страниц, статьи, новости, FAQ и контент-план. Не меняет код и не переименовывает URL.

### Технический редактор

Отвечает за русский деловой текст, терминологию, точность формулировок, отсутствие лишних англицизмов, юридически и коммерчески безопасные обещания. Не меняет код и структуру страниц.

### AI-дизайнер

Отвечает за визуальную иерархию, первый экран, CTA, блоки доверия, карточки, таблицы, читаемость и мобильную версию. Не удаляет SEO/GEO-блоки ради красоты и не предлагает тяжелые визуальные решения без пользы.

### Frontend-разработчик

Готовит или реализует утвержденное ТЗ в Next.js, React, TypeScript и Tailwind. Кодовые изменения допустимы только в отдельной ветке, только с согласованными файлами, после scope от Архитектора.

### QA-тестер

Проверяет diff, сборку, lint/typecheck, ключевые маршруты, мобильные ширины, формы заявок, SEO/GEO-основу и готовность к merge.

## 4. Режимы субагентов

Постоянные project-scoped субагенты в `.codex/agents` работают read-only. Они анализируют, уточняют, готовят ТЗ и проверочные списки, но не меняют файлы.

Кодовые изменения выполняются только так:

1. Архитектор формирует утвержденный scope.
2. Создается отдельная ветка под конкретный пул задач.
3. Основной Codex или явно назначенный worker вносит правки только в разрешенные файлы.
4. QA проверяет результат.
5. Архитектор делает review.
6. Только после этого изменения можно коммитить и готовить merge в `ai-site-dev`.

## 5. Production-ready рабочий цикл

### 5.1. Постановка задачи

Андрей или Архитектор формулирует:

- цель;
- бизнес-контекст;
- затронутые страницы;
- что нельзя трогать;
- ожидаемый результат;
- нужен ли код или только аудит.

Архитектор фиксирует:

- текущую ветку;
- `git status --short --untracked-files=all`;
- режим задачи;
- потенциальные P0/P1/P2 риски;
- нужны ли субагенты.

### 5.2. Анализ субагентами

Архитектор запускает только нужные роли:

- маркетолог — если задача про оффер, SEO/GEO, контент, статьи, доверие;
- технический редактор — если нужны тексты, русификация, безопасные формулировки;
- дизайнер — если есть визуальная иерархия, CTA, мобильная подача;
- frontend-разработчик — если нужен file-scope и план правки;
- QA-тестер — если нужно проверить готовность к merge.

Субагенты работают read-only и возвращают findings Архитектору.

### 5.3. Сводное решение Архитектора

Архитектор собирает:

- что делать;
- что не делать;
- какие файлы можно менять;
- какие файлы нельзя трогать;
- какие проверки нужны;
- какой rollback;
- какой первый безопасный пул задач.

Если есть противоречие между агентами, решение принимает Архитектор.

### 5.4. Утверждение scope

Перед кодом обязательно зафиксировать:

- ветку;
- task code;
- разрешенные файлы;
- forbidden-зоны;
- критерии приемки;
- проверки;
- кто делает реализацию;
- нужен ли визуальный review Андрея.

Если scope затрагивает формы, API, routes, metadata, JSON-LD, sitemap, robots, env, production, юридические данные, цены или гарантии — требуется отдельное явное подтверждение.

### 5.5. Отдельная feature-ветка

Все изменения идут через отдельную ветку от актуальной `ai-site-dev`.

```text
ai-site-dev
  -> feature/site-YYYYMMDD-short-task-name
  -> fix/site-YYYYMMDD-short-fix-name
  -> content/site-YYYYMMDD-topic-name
  -> docs/site-YYYYMMDD-ai-team-change
```

Нельзя смешивать разные пулы задач в одной ветке.

### 5.6. Внесение изменений

Основной Codex или worker меняет только утвержденные файлы.

Запрещено:

- `git add .`;
- попутные рефакторы;
- переименование URL без scope;
- изменение API/форм без scope;
- скрытые изменения metadata/JSON-LD/sitemap/robots;
- deploy или merge в `main`.

### 5.7. Diff

После правок:

```bash
git status --short --untracked-files=all
git diff --name-only
git diff --check
```

Diff должен содержать только ожидаемые файлы.

### 5.8. Проверки

Минимум:

```bash
npm run build
```

Если доступны и не требуют интерактивной настройки:

```bash
npm run typecheck
npm run lint
```

Если менялись `.toml`-профили:

```bash
python3 -c 'import pathlib,tomllib; [tomllib.loads(p.read_text()) for p in pathlib.Path(".codex/agents").glob("*.toml")]; print("TOML parse OK")'
```

### 5.9. QA

QA проверяет:

- список измененных файлов;
- сборку;
- typecheck/lint;
- ссылки;
- ключевые маршруты;
- формы/CTA, если затронуты;
- SEO/metadata/JSON-LD, если затронуты;
- мобильные ширины 360, 375, 390, 400, 430 px для видимых правок.

### 5.10. Review Архитектора

Архитектор перед commit проверяет:

- соответствует ли diff scope;
- не затронуты ли forbidden-зоны;
- нет ли неподтвержденных фактов, цен, гарантий и характеристик;
- не сломаны ли SEO/GEO и мобильная логика;
- есть ли понятный rollback.

### 5.11. Commit и merge

Commit допустим только после проверок и review.

Merge в `ai-site-dev` допустим только после:

- чистого или понятного `git status`;
- успешного build;
- QA-вердикта;
- review Архитектора;
- подтверждения Андрея, если задача чувствительная.

`main`, production deploy и инфраструктуру не трогать без отдельного прямого подтверждения Андрея.

## 6. Project guardrails РОСПАРК

### 6.1. Коммерческие guardrails

Запрещено без отдельного подтверждения:

- публиковать цены на отдельные элементы и оборудование;
- обещать точную окупаемость;
- обещать гарантированный рост заявок или доходности;
- обещать внедрение за фиксированный срок без исходных данных;
- обещать 100% распознавание номеров;
- обещать абсолютную безотказность.

Стоимость можно обсуждать только как факторы сметы:

- количество въездов и выездов;
- тип объекта;
- сценарии доступа;
- оплата;
- интеграции;
- условия монтажа;
- требования к отчетности и сопровождению.

### 6.2. Технические guardrails

Запрещено выдумывать:

- технические характеристики;
- сертификаты;
- ГОСТы;
- гарантию;
- ресурс циклов;
- точность распознавания;
- совместимость;
- сроки реакции поддержки;
- клиентов и кейсы.

Все технические факты брать только из подтвержденных документов проекта, карточек оборудования, PDF, паспортов, договоренностей с Андреем или иных явно указанных источников.

### 6.3. Архитектурные guardrails

Только по отдельному разрешению менять:

- формы и поля форм;
- `/api/lead`;
- `/api/quiz`;
- отправку на почту, MAX, Telegram;
- маршруты и URL;
- metadata, canonical, OpenGraph;
- JSON-LD;
- sitemap;
- robots;
- navigation, Header, MobileMenu;
- env/PM2/production;
- GitHub Actions;
- DNS, SSL, VPS, Caddy, nginx.

### 6.4. Стиль публичных страниц

Публичные страницы РОСПАРК должны звучать:

- конкретно;
- технически аккуратно;
- по-русски;
- в B2B-стиле;
- без маркетинговой воды;
- без агрессивных обещаний;
- с понятной пользой для директора, управляющей компании, инженера и службы безопасности.

## 7. Обязательный QA-checklist

Для каждого пула задач:

```text
[ ] git status --short --untracked-files=all
[ ] git branch --show-current
[ ] git diff --name-only
[ ] git diff --check
[ ] TOML parse, если менялись .toml-профили; если нет — N/A
[ ] npm run build
[ ] npm run typecheck, если скрипт есть
[ ] npm run lint, если скрипт есть и не требует интерактивной настройки
[ ] проверка ссылок и ключевых маршрутов
[ ] SEO/metadata/JSON-LD проверка, если изменялись страницы/SEO-зоны
[ ] адаптив 360/375/390/400/430 px для видимых UI-правок
[ ] формы и CTA, если затронуты заявки
[ ] review Архитектора
[ ] итоговый отчет для Андрея
```

Если проверку нельзя выполнить, нужно явно указать почему.

## 8. Runbook: как запускать агентный цикл на новой задаче

### Шаг 1. Пользователь формулирует задачу

Пример:

```text
Нужно улучшить SEO/GEO страницы /oborudovanie. Код пока не менять.
```

### Шаг 2. Архитектор фиксирует старт

```bash
git status --short --untracked-files=all
git branch --show-current
```

Архитектор определяет режим: audit, brief, code-plan, implementation, QA.

### Шаг 3. Архитектор выбирает субагентов

Пример:

```text
Маркетолог: проверить спрос, структуру, FAQ.
Редактор: проверить формулировки и обещания.
Дизайнер: проверить первый экран и CTA.
Frontend: определить file-scope.
QA: подготовить проверки.
```

### Шаг 4. Субагенты возвращают read-only выводы

Каждый агент возвращает отчет в своем формате: findings, risks, safe next tasks, read-only confirmation.

### Шаг 5. Архитектор собирает единое решение

Архитектор выдает:

- цель;
- первый безопасный пул;
- файлы;
- запреты;
- проверки;
- rollback;
- критерии приемки.

### Шаг 6. Андрей утверждает scope, если задача чувствительная

Отдельное подтверждение нужно для:

- форм/API;
- routes;
- metadata/JSON-LD/sitemap/robots;
- юридических данных;
- цен и гарантий;
- production/deploy;
- main.

### Шаг 7. Создается ветка

```bash
git checkout ai-site-dev
git checkout -b feature/site-YYYYMMDD-short-task-name
```

Если `ai-site-dev` не актуальна или есть незакоммиченные изменения, Архитектор останавливается и предлагает безопасный следующий шаг.

### Шаг 8. Вносятся изменения

Правятся только файлы из scope. Никаких попутных улучшений.

### Шаг 9. Проверки

```bash
git diff --name-only
git diff --check
npm run build
npm run typecheck
```

`npm run lint` — только если не требует интерактивной настройки.

### Шаг 10. QA и review

QA дает вердикт ready/not-ready. Архитектор проверяет scope и риски.

### Шаг 11. Commit

```bash
git add <точные файлы>
git commit -m "<type(scope): message>"
```

Запрещено `git add .`.

### Шаг 12. Merge

Merge в `ai-site-dev` — только после review и подтверждения, если требуется.

Production deploy — отдельная задача и отдельное прямое разрешение.
